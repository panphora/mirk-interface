# HISTORY

A chronological, **append-only** log of every meaningful decision on this project. **Decision + reasoning, one bullet each, kept tight.** Purpose: a portable "lessons learned" so we can apply this thinking to a future UI kit without re-discovering it.

Conventions:
- Add a one-liner here whenever a decision is locked. If a prior decision is reversed, add a *new* entry — never edit or delete the old one.
- The current accepted state lives in `DECISIONS.md`; this file is the audit trail of how we got there.
- Keep entries terse — the *why* is what matters.
- Group by date the decision was made.

---

## 2026-04-26

- **Reference systems: Primer + Carbon.** Both are designed by companies (not individuals), so they're more likely to embed real accessibility and best-practice work at scale. Studying two cross-checks each other — what one team misses, the other often catches. Goal of mirk is performant, small, *and* best-practices, so we mine both.
- **3-column showcase layout (Primer | Carbon | mirk).** Visual side-by-side comparison while building, so every mirk component is judged against best-in-class peers in real time.
- **Build components from scratch, one at a time, simple → complex.** Establishes form-composition primitives, focus-ring conventions, and theming on cheap components before tackling expensive ones; gives every component a clean ADR rather than a rushed batch.
- **Light + dark mode are first-class.** mirk drops into other devs' pages — we don't control the host theme, so both modes have to be peers from day one, not one with the other bolted on.
- **Pure HTML + CSS only. No DIY JavaScript. No web components.** Components must be copy-pasteable; `document.documentElement.outerHTML` must round-trip state. Native elements give us a11y, keyboard handling, form participation, and serialization for free.
- **Default to native form elements; CSS-only state via `:checked`, `:has()`, `:focus-within`, etc.** Falls out of the pure-HTML rule — fewer moving parts than anything else.
- **When native isn't enough, use a curated third-party plugin and style it. We never write our own JS components.** Battle-tested plugins beat DIY JS; no init scripts for users to maintain.
- **Styling: Tailwind.** Compact, HTML-first, familiar to most devs, portable; fits the copy-paste-a-snippet model and aligns with the hyperclay ethos.
- **Rich text engine: overtype.dev.** Self-authored, so bug fixes are in our hands. Performant and small enough that 20 instances on one page work fine (TinyMCE chokes at that scale). Easy for devs to integrate, looks nice.
- **Tags and multi-select: deferred.** They need JS, but more importantly they're advanced patterns most forms genuinely don't need; users find them less familiar. Reach for the simpler core components first.
- **Decision-log discipline: per-decision ADR file under `decisions/`, numbered, never renumbered, superseded files stay in place.** Lets us unwind a decision cleanly if it turns out wrong, remember why we did something months later, and avoid re-litigating dead ends.
- **Repo layout: `README.md` (locked rules), `PLAN.md` (tasks), `decisions/` (verbose ADRs), `HISTORY.md` (this file — concise log), `refs/` (read-only upstream sources).** Each file has a single job so they don't drift into each other.

## 2026-04-27

- **Single-select dropdown: native `<select>` with `appearance: base-select`, progressive enhancement.** We want robust cross-browser support today (the OS popup is the universal fallback everywhere); where modern engines support `base-select` we get a fully-styled dropdown matching the rest of mirk for free, no JS required.
- **Decision tracking restructured.** `decisions/` folder (per-file ADRs, never renumbered, superseded files left in place) replaced by a single top-level `DECISIONS.md` (living doc, current state only, edited freely) plus a new top-level `UNDECIDED.md` for active brainstorming. `HISTORY.md` becomes the append-only audit trail — *this* file is what guarantees we never lose the *why*. Reason: we don't need two parallel records of every decision; one current-state file + one immutable log is enough, with fewer small files to navigate.
- **Theming locked: Tailwind v4 via CDN (`@tailwindcss/browser`), class-based dark mode (`@custom-variant dark (&:where(.dark, .dark *))`), every component rendered in light AND dark side-by-side on every dev page.** No toggle: parity bugs become invisible the moment you forget to flip it. Rendering both at once makes regressions immediate. `prefers-color-scheme` is deferred until we publish demos. See `DECISIONS.md` 0001.
- **Color tokens: stock Tailwind defaults until 3–4 components reveal the palette we actually use.** Picking colors before they're earned over-specifies; harvesting later is cheaper than reshuffling.
- **Focus ring locked: 1px outline, 2px offset, `:focus-visible` only, `outline` not `box-shadow`.** Thin ring + clear offset reads as a layer rather than a chunky border; offset prevents stacking with element borders; outlines survive `overflow: hidden` whereas shadows don't. See `DECISIONS.md` 0002.
- **Buildless Primer in `compare.html` doesn't work — `esm.sh`'s `*.module.css.mjs` files 301-redirect to `text/css` URLs that Chrome's module loader rejects, and Primer's UMD bundle throws inside styled-components from a peer-version mismatch.** Tested in isolation: `lodash@4` and `lit@3` import cleanly via the same path, so the failure is specific to Primer. Eliminates esm.sh / UMD as paths forward.
- **`compare.html` loader: Vite dev server, `compare.html` only.** Run `npm run dev`. Vite resolves `@primer/react` + bundles its CSS modules. Carbon stays on its own CDN scripts (works without install). Scope is strictly the comparison tool — `index.html` and every mirk component stay 100% buildless. Reason: the dev tool earns the build step; the deliverables don't. See `DECISIONS.md` 0003.

## 2026-04-28

- **Font locked: Departure Mono, used uniformly across every mirk component.** We compared Geist Mono, Departure Mono, Geist Pixel, and IBM Plex Mono on buttons + dropdowns side-by-side in `experiments/experiments.html`. Geist Mono and IBM Plex Mono are easier to read at small sizes — but mirk's whole design promise is to be **violently obvious**: a callback to 80s/90s UIs that were plain, easy to interact with, and unambiguous about what was clickable. A pixel face commits to that vocabulary; a clean modern mono softens it. Departure Mono wins because it's a pixel font that's still legible enough at the larger-than-default sizes mirk uses, and it telegraphs the "simple, basic, obvious" stance from the first glance. See `DECISIONS.md` 0004.
- **No pure white, no pure black anywhere in mirk.** `#ffffff`/`#000000` (and the Tailwind `text-white`/`bg-black`/`border-white`/etc. utilities) are banned across components, demos, and snippets. Pure values are perceptually harsh — irradiation makes white-on-dark hairlines bloom, and pure black gives no headroom for hover/active emphasis. Current canonical off-values: dark panel fg `#F6F7F9`, light panel fg `#0B0C13`, light panel bg `#F7F2EA`. Confirmed visually in `experiments/experiments.html` while tuning the dropdown focus ring (1px outline read thicker on the dark panel; softening dark-mode focus to `#bfbfbf` was the first concrete payoff of this rule). See `DECISIONS.md` 0005.
- **Docs: concise, information-dense.** Every md file in this repo (README, PLAN, DECISIONS, HISTORY, UNDECIDED, plan-folders, etc.) prefers density over completeness — bullets over paragraphs, only the *why* that isn't derivable from code, lead with the rule then one line of context. Eat the dog food: a UI kit valuing brevity writes its docs the same way. See `DECISIONS.md` 0006.
- **Form controls share one line-height: `leading-normal` (1.5), explicit on every snippet.** Caught while a button rendered 44px and a dropdown 39px on identical padding — the only difference was the button inheriting `1.5` from `<html>` while the dropdown carried `leading-tight` (1.25). One default for the whole kit means buttons / selects / inputs / textareas line up by themselves when placed in rows or stacks; explicitness on each snippet means no surprises when copy-pasted into a host page with different inherited values. See `DECISIONS.md` 0007.
- **Compliance fix + pattern: focus rings only on `:focus-visible`, even for wrapped controls.** Caught dropdowns using `focus:[outline:…]` (violated 0002 — outline appeared on mouse click). Rect dropdown switched to `focus-visible:`. Round dropdown's gradient pill wraps the `<select>`, so the wrapper needs `has-[:focus-visible]:[outline:…]` (not `focus-within:`, which also triggers on click) and the inner select keeps `focus:outline-none` to suppress UA's default. 0002 updated with this wrapped-control rule.
- **`<select>` keeps the outline on mouse click — accepted as native UX.** Chromium and Firefox both apply `:focus-visible` to `<select>` even on click (the OS popup is keyboard-navigable, so the browser treats click as entering keyboard mode). Buttons don't behave this way. We accept this for selects: matches native cross-web behavior, and the alternatives (JS widget or `:focus:not(:focus-visible)` hacks) violate locked rules or cause flicker. 0002 updated with this exception.
- **`text-box-trim` deferred (not undecided) until ~1 year after Firefox ships.** Was sitting in `UNDECIDED.md`, but it's not actively being weighed — it's gated on browser support we can't influence. Adopting now means snippets ship a property Firefox ignores → silent visual drift, exactly what `0001` (both-themes-shown) exists to catch. Tuned `py-` + `leading-normal` already gives the same result portably, and the property will force re-tuning when it lands anyway, so doing it once on a stable baseline is cheaper. Moved to `DECISIONS.md` 0008.

## 2026-04-29

- **Workflow order — left flexible by design.** Rule 4 was briefly locked as "Build first, then decide" (during the text-input session); reverted to "Either order — build first or decide first. Pick whichever fits the work." Some choices are clearer after prototyping (visual feel, asymmetric tuning); others need a contract before code (a11y, semantics, API shape). Locking one direction would force the wrong workflow on half the components. Recording this so a future reader knows the looseness is intentional, not an oversight.
- **Text input: solid uniform border, two variants (rect + 5px-rounded).** First form component. Containers vs. pressables — bevels say "press me" (buttons), uniform borders say "this holds content" (inputs). Two variants cover sharp/industrial vs. softened without proliferating styles. Took Primer's uniform border (1px), dropped its inset shadow (would compete with our bevel buttons next door). Rejected Carbon's underline-only — we want a frame, not a hint. See `DECISIONS.md` 0009.
- **Per-panel CSS vars when bevel semantics don't translate.** When light/dark need *opposite* directions along the same axis (e.g., border darker-than-bg in light, lighter-than-bg in dark), introduce a dedicated per-panel var (`--input-border`, `--placeholder-color`) rather than aliasing an existing bevel var. Bevel-tl/bevel-br are parallel across panels (tl = highlight, br = shadow), so they can't carry asymmetric values. Reuse aliases unrelated colors (e.g. focus-color doubling as placeholder), which makes future tuning silently risky. Keeps component HTML identical across panels. See `DECISIONS.md` 0010.
- **Placeholder color: explicit hex, never opacity.** Opacity isn't a color — it dims whatever's underneath, so the rendered color depends on the bg behind it. An "explicit color" defined via opacity stops being the chosen value the moment the underlying surface changes. Discovered by tracing why a "too gray" dark placeholder was actually browser-default-gray × 50% alpha rather than the bevel-fg we thought we were dimming. See `DECISIONS.md` 0011.

## 2026-05-14

- **Stateful-indicator rule locked: flat off, pressed-in bevel selected.** Checkbox, radio, and segmented segments share one visual grammar. Off looks like a text-input container slot (1px `--input-border`, flat). Selected looks like a depressed rect button (gradient fill plus pressed-in inset-shadow bevel). Implemented via `box-shadow inset` so size doesn't change on selection. Toggle thumb and slider thumb are exempted because they're handles, not indicators; state lives in track and fill geometry, not on the thumb surface. See `DECISIONS.md` 0012.
- **Rect vs round axis locked, per-component mapping.** One organizing axis (sharp/industrial vs softened) with component-specific interpretation: corner radius for inputs and text-like containers, indicator shape for radio, track and thumb geometry for toggle, end-cap radius for segmented, thumb shape for slider. Reason for the per-component variation: forcing a single literal mapping (e.g., "round always means corner radius") would collapse the axis for components with inherent shape (radio, toggle). Table in `DECISIONS.md` 0013.
- **DIY JS rule relaxed for six named components.** Number stepper, slider visual bridge, date-range cross-validation, file-picker filename display, image preview, tags add/remove. The default ("no DIY JS") stays. Each name is forced by a concrete native limitation: no CSS hook for `<input type=file>` value, no thumb-position read on `<input type=range>`, no native combined date range, no `::after` on replaced elements for icons. README's "No DIY JavaScript" bullet now links to `DECISIONS.md` 0014.
- **Textarea: text-input plus `resize: vertical`.** One added rule on top of 0009. Vertical-only is the sane default. Disabling resize is overbearing on long content. Horizontal resize breaks surrounding layout. See `DECISIONS.md` 0015.
- **Radio: square-radio exception for the rect variant.** Convention is "radios are round"; the kit's axis is "everything ships rect plus round." We honor the axis with a square indicator plus square inner fill in rect, "single-choice tile" feel. Visually distinct from checkbox (square plus ✓) and from round radio (circle plus dot). See `DECISIONS.md` 0016.
- **Toggle: flat track plus always-beveled thumb.** Track is the container (bg shifts on state: `--bevel-bg` off, `--accent` on). Thumb is a handle (always beveled, never flat). State equals track color plus thumb position, not the thumb surface. See `DECISIONS.md` 0017.
- **Segmented: grouped radios with sibling-selector CSS, no JS.** `<label>` wraps each `<input type=radio>` plus styled span; `-ml-[1px]` collapses adjacent borders to one hairline. Border-width constant at 3px across states; only colors swap on selection, so segments don't shift size when clicked. See `DECISIONS.md` 0018.
- **Slider: visual layer in CSS divs, native range drives state.** No CSS-only path matches the bevel aesthetic across browsers (range pseudo-elements are too divergent and don't carry filled-portion gradient cleanly). Wrapper div plus track plus filled portion plus thumb, with the native `<input type=range>` overlaid `opacity: 0` and `z-10` for interaction capture. Tiny JS mirrors `.value` into a `--value` CSS prop on the wrapper. See `DECISIONS.md` 0019.
- **Date / time / datetime: hide UA chrome, overlay our glyph.** `::-webkit-calendar-picker-indicator { opacity: 0 }` positioned over the whole input opens the picker on click anywhere. Departure Mono glyph (`□` for date, `◌` for time) sits on the right edge, matches the dropdown's `›` pattern. Closed-state visual unified across browsers. See `DECISIONS.md` 0020.
- **Date range: two date inputs plus JS cross-validation.** Single combined-popup picker would buy marginally nicer UX at the cost of a calendar-rendering library. Not worth the bytes. JS is two lines: sync `min` and `max` on change. See `DECISIONS.md` 0021.
- **File picker: hidden input plus label-as-button plus JS filename.** No CSS hook on `<input type=file>` value, so JS is the only way to show the filename inline. Bevel button (rect or round per 0013), flat container next to it for the filename text. See `DECISIONS.md` 0022.
- **Image input: file picker plus FileReader preview.** Same construction as file picker, plus a preview square populated via `FileReader.readAsDataURL` on change. Preview square is a container (flat frame, aspect-square). See `DECISIONS.md` 0023.
- **Tags: built; reverses 2026-04-26 deferral.** Tags now ship as a real component with small JS for add/remove. Reason for reversal: the named-exception discipline in 0014 absorbs the JS cost transparently, and tag inputs are common enough in modern forms that mirk would feel incomplete without one. Multi-select stays deferred (genuinely heavier to implement well). Original 2026-04-26 entry stays per audit-trail rule. See `DECISIONS.md` 0024.

### Visual review pass (later same day)

- **Stateful-indicator rule INVERTED: bevel on unselected, flat on selected.** Earlier in the day we locked "off=flat, selected=pressed-in bevel" for checkbox / radio / segmented (the metaphor was "I pressed it and it stayed in"). Visual review found checkboxes "too busy" with the bevel-on-selected, and noticed that the round radio's bevel state actually read as the *unselected* affordance: it looked clickable, like a button waiting to be pressed. Switched the rule: bevel = unselected ("this is interactive, click me"), flat-with-mark = selected ("this has been confirmed"). The 2026-04-26 metaphor was logically clean but the new pattern wins on first glance — the kit is meant to be obvious, and a flat box with a check is more obviously "this one is on" than a depressed bevel. `DECISIONS.md` 0012 rewritten.
- **Checkmark: CSS-drawn, sharp-edged, longer rising stroke.** Unicode `✓` in Departure Mono reads small and slightly rounded. Switched to a 2-border rotated-rectangle construction (right + bottom borders on a `w-[6px] h-[13px]` div rotated 45deg). Width-to-height ratio ~1:2 gives the asymmetric proportions of a real checkmark (longer rising arm). Borders give crisp pixel-aligned edges with no font dependency. Color is `--bevel-fg`.
- **Toggle: transparent track, darker thumb via new per-panel vars (`--ctrl-bg`, `--ctrl-hi`, `--ctrl-lo`).** The original "track has `--bevel-bg` background, thumb uses bevel-gradient" looked "pasty" in light mode — the cream thumb on a beige track had no contrast. Removed the track fill entirely (track is now just a border outline on the panel canvas), and the thumb gets its own darker color: medium-brown (`#8C7660`) in light, medium blue-gray (`#5F6582`) in dark. The thumb still has its bevel (gradient frame + inner solid in round; 4-side bevel in rect) but the *colors* are now distinct from the bevel-button palette so toggles don't compete with buttons. `DECISIONS.md` 0017 updated.
- **Segmented control: removed from scope.** Visual review flagged it as the weakest part of the scaffold. The rationale for keeping it (button-group affordance for set-of-options) collapses on inspection: a radio button group does the same job with a more familiar pattern, and we already have radios with two variants. Removed from `experiments.html`, `README.md` Component scope list, `PLAN.md` build order, and `DECISIONS.md` 0018 rewritten as "removed." Future: if the segmented affordance genuinely matters somewhere, we'd revisit, but no current need.
- **Slider: filled portion flat (no gradient).** Kept the beveled thumb (user explicitly liked it). Flattened the filled portion to a single solid color (`--ctrl-bg`, same as toggle thumb). The gradient on the filled length read as "this is interactive, drag me" — same cue the thumb carries — so duplicating it on the track made the whole component feel too prominent. The thumb alone now carries the "interactive" signal; the filled portion just says "this much value." `DECISIONS.md` 0019 updated.
- **Date / time / datetime: typing works again.** Previous implementation made `::-webkit-calendar-picker-indicator` span the entire input area, which intercepted clicks for the picker and prevented focus on the typing segments. Confined the indicator to a right-edge strip (`right: 0; top: 0; bottom: 0; w-[44px]`), so clicking the left portion focuses for keyboard typing and clicking the right edge (where our glyph is) opens the native picker. Both affordances are now reachable. `DECISIONS.md` 0020 updated.
- **Number input: removed border-l between input and stepper column.** Visual review noted the divider line "distracts a little bit." The stepper buttons already have their own bevel borders that visually separate them from the input; the extra 1px container divider was redundant. Cleaner without it.
- **File picker: previous 0022 decision reversed; moved to `UNDECIDED.md`.** The original lock (label-as-button + adjacent flat-frame for filename) was abandoned because the round variant couldn't share a border with the filename frame, creating a visual inconsistency between rect and round. Two new styles in play: (A) compact — small chip-like button inside the filename container; (B) button + plain text — full bevel button next to plain filename text with no shared frame. Both styles rendered in both rect and round variants in `experiments.html` (4 file picker sections total) for direct comparison. `DECISIONS.md` 0022 removed.
- **Indicator bevel direction flipped: raised, not depressed.** The just-inverted rule (bevel on unselected, flat on selected) shipped with the bevel oriented "dark top-left, light bottom-right" (pressed-in). Visual review found that read as already-activated rather than waiting-to-be-pressed: a depressed slot suggests "I clicked this and it stuck," which is the *opposite* of what an unselected indicator should communicate. Swapped the box-shadow colors (`inset 2px 2px 0 var(--bevel-tl), inset -2px -2px 0 var(--bevel-br)`) so light sits on top-left and dark on bottom-right, matching the rect button's pressable bevel. Now an empty checkbox looks like a tiny button-slot asking to be pressed, exactly mirroring the affordance language of the kit's other pressables. Applied to checkbox rect, checkbox rounded, and radio rect; round radio uses a gradient frame (no inset shadow) and was already in pressable orientation. `DECISIONS.md` 0012 updated.

## 2026-05-15

- **Checkmark geometry tightened.** Stroke 2px → 2.5px (more visible without becoming chunky), tail 13px → 12px (was overhanging the indicator), nudged 0.5px down and 0.5px right (the unrotated bounding box was sitting slightly high-left after the 45deg rotation; small translate restores optical center). Short arm (6px width) unchanged. `DECISIONS.md` 0012 spec line updated.
- **Round radio bounding box bumped 22 → 26px while rect indicators stayed at 22px.** Perceptual rule: a circle inscribed in a `w×h` box covers `π/4 ≈ 78%` of the square's area, and the eye weighs area more than bounding box, so an equal-w/h circle reads smaller next to a square. The round radio sitting next to a rect radio of identical dimensions felt undersized; bumping just the circle brought them to perceptual parity in a column. Inner dot (`7×7px`) left alone for now — to be revisited if the dot starts to feel lost. New "Sizing: round indicators get a perceptual bump" subsection in `DECISIONS.md` 0013 captures the rule so the next round/rect pairing inherits it.
- **Round radio center dot bumped 7 → 9px.** With the outer circle at 26px, the 7px dot dropped from 32% of the frame (at the original 22px outer) to 27% — visibly lost. 9px restores the ratio to ~35%, slightly more prominent than the original 7-of-22 reading because the larger outer can carry it without crowding. `DECISIONS.md` 0012 center-mark spec updated.
- **File picker: keep all four variants, ship them as a 2×2 matrix.** The yesterday-reopened question ("pick Compact or Button+Text, in Rect or Round") resolved as "ship all four." Two styles serve genuinely different contexts: Compact suits dense field columns where every row wants the same outer rectangle; Button+Text suits action rows where the button is a peer to other buttons and the filename is freestanding metadata. Locking one would force a wrong fit roughly half the time; the kit already accepts that one decision per component isn't always enough (the rect/round axis exists for the same reason). New `DECISIONS.md` 0022 added with the matrix and the Compact / Button+Text definitions. `0013` table cell points at `0022` for the style axis. `0023` (image input) committed to Button+Text style explicitly, since the preview square plays the role Compact's filename frame plays elsewhere. File picker section removed from `UNDECIDED.md`.
- **Axis exception: checkbox and radio each ship one variant only.** Removed the rounded-corner checkbox and the square-cornered radio. The kit's axis is "every component ships rect + round," but shape carries the convention for these two controls: rounded checkboxes don't read as checkboxes (more like soft chips), and square radios read as tiles or single-select buttons. Tried both during the scaffold pass; both failed the obviousness test on visual review. The clarity-for-users rule beats the axis-completeness rule here. Updates: `0013` table rows for Checkbox and Radio show single variants and `—` for the absent column, with a new "Axis exceptions" section below the table; `0016` (the square-radio exception) marked REMOVED with a backpointer to this entry; `0012` rewritten so the Unselected / Selected bullets are keyed off the component name (Checkbox, Radio) rather than the rect/round axis. `experiments.html` lost the four removed sections (2 per panel) and the remaining labels are now plain "Checkbox" and "Radio."
- **Checkbox construction switched from gradient + inset box-shadow to solid bg + real CSS borders.** Three fix variants were rendered side-by-side in both panels (V1 = inset BR swapped to `--input-border`; V2 = gradient + 1px hairline; V3 = solid `--bevel-bg` + bevel inset, no gradient). User picked V3, then noticed the inset-shadow construction couldn't produce the 45° diagonal miter that the rect button's real CSS borders produce — inset shadows are overlapping rectangles, not mitered borders. Final V3 swaps the inset shadow for `2px` real CSS borders with per-side colors (top + left `--bevel-tl`, right + bottom `--bevel-br`). Selected state keeps the same `2px` width but uniform `--input-border` color across all four sides, so the inner content area is constant between states (no layout shift). Root cause of the original problem was a color collision: the gradient's bottom anchor and the bottom inset shadow were both `--bevel-br`, so the bottom edge had zero contrast against itself — especially visible in light mode where the bevel range is only ~22 RGB units per channel vs. ~50 in dark. Real borders also gain the button's mitered-corner geometry as a free side-effect, restoring visual continuity with the rect button and dropdown. `DECISIONS.md` 0012 Decision section rewritten for the new construction, with a new "Construction: real CSS borders, not inset box-shadow" subsection documenting the collision and the fix.
- **Radio selected-state ring aligned with checkbox selected-state ring.** Was `inset 0 0 0 1px var(--input-border)` (1px hairline via box-shadow); now `border: 2px solid var(--input-border)` (real CSS border, same width and color the checkbox selected state uses). Reason: when checkbox and radio sit in the same form, their selected states should share one frame vocabulary so users read "this control is set" as a single visual pattern. The hairline-vs-border mismatch was a subtle but real inconsistency. Outer `26×26` stays fixed via border-box, so the radio's perceived outer edge doesn't shift between off and on. Off state unchanged (gradient frame + inner pill — that's the round-button affordance and shouldn't be flattened to match the rect button's vocabulary). `DECISIONS.md` 0012 radio selected-bullet rewritten.
- **New per-panel CSS var: `--mark-fg`.** Used by the checkmark and the radio inner dot. Was `--bevel-fg` (the body-text color: `#F6F7F9` dark, `#15120e` light). The marks at full text contrast felt harsher than the rest of the kit, especially the check on light-mode cream. New values are `#B5B9CC` dark (a step down from off-white into the blue-gray bevel family — same family as `--input-border` and `--bevel-tl`, just brighter) and `#4A3A2B` light (near-black warmed up with brown undertones, sitting between `--bevel-fg` and `--input-border`/`--ctrl-bg`). Both pick up the panel's own color family rather than introducing a new hue. Reason for a new var, not just a darker `--bevel-fg`: body text and marks have different jobs. Text wants maximum readability; marks are confirmation glyphs sitting on top of a deliberately soft `--bevel-bg` and should feel like a step inside the kit's palette, not a hard punch through it. `--bevel-fg` continues to serve labels, input text, button text. `DECISIONS.md` 0010 in-use list extended; `0012` mark color refs swapped to `--mark-fg`.
- **`--mark-fg` retuned upward via an interactive slider.** First-pass values (`#B5B9CC` dark, `#4A3A2B` light, set in the bullet just above) read too low-contrast in practice — the check and radio dot lost themselves against `--bevel-bg`. Built a temporary fixed-bar tuner at the top of `experiments.html`, one range slider per panel, each linearly interpolating between the current value (slider 0) and the previous `--bevel-fg` (slider 100, full text contrast). Iterated visually; landed at `#E1E3EA` dark (~67% of the way toward `--bevel-fg`, now close enough to off-white that the first-pass framing of "a step into the blue-gray bevel family alongside `--input-border` / `--bevel-tl`" no longer applies — it's basically `--bevel-fg` with a faint cool tilt) and `#3F3225` light (~20% of the way, still warm-brown undertone, just slightly darker than first-pass). Dark took most of the correction; light needed only a nudge, which suggests the cream `--bevel-bg` was already doing more contrast work for the mark than the dark `--bevel-bg` was. Tuner removed after the values landed. Updates `experiments.html` only; `DECISIONS.md` doesn't carry the hex values for `--mark-fg`, so no decision-record edits needed.
